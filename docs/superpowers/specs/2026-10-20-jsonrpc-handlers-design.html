JSON-RPC handlers: finishing the port

Branch pv/handlers · based on c72e2448 · 2026-10-20 · design spec, for planning

The one idea. A handler validates its params and returns a thunk; the JSON-RPC layer runs the thunk and wraps the outcome as either result or error. That split is what lets tests call DashiBase.apply_handlers on a payload with no server. This work finishes the port: it makes the layer actually JSON-RPC 2.0, makes result/error the only success signal, settles HTTP status codes, moves the frontend onto the three endpoints, and cuts the test suite down to behaviour that matters.

1. Intent

The team lead reviewed the handlers and asked for a clean separation between check (build the thunk; throw on bad params) and execution (run the thunk), so issues can be debugged by executing a function on a payload. On this branch he already reshaped the handlers and the tests around apply_handlers, and limited live-server tests to one example each of /rpc, /rpc-probe, /rpc-stream plus CORS. What remains is listed below.

Goals

  1. The server is a JSON-RPC 2.0 server, verified by tests that go through the string parser.
  2. No reply uses valid to say whether a request succeeded; that is result vs error.
  3. HTTP status codes are fixed: per-error on /rpc-stream, always 200 elsewhere.
  4. The frontend speaks JSON-RPC to the three endpoints.
  5. The test suite is substantively smaller: tautologies cut, broken tail rewritten without a server.
  6. ExperimentTracking drops its own copy of the JSON-RPC layer and uses DashiBase's, in the same piece of work.

Non-goals

  • Reworking handler logic, issue shapes, or the probe's semantics.
  • New features or a new frontend architecture. The only route beside the three endpoints is the GET download in 4.3.
  • String ids (the spec allows them; we deliberately accept integers only).

Anti-goals (a failure even if it works)

  • A large diff. Footprint is judged by lines added; the test suite should shrink by hundreds of lines.
  • Any UI behaviour change visible to an author: same messages, same marks on cards, same Run behaviour.
  • Tests that restate a definition (a constant equals itself, a field is what was just set, a literal's shape).

2. Constraints

  • Minimal source changes. DashiBase/src and DashiBoard/src change only where a goal above requires it.
  • Every Julia change outside dashiboard-ui carries its functional reason in a docstring or comment. Comments state purpose, not history (no dates, measurements, "used to").
  • Docstrings that describe {valid: true, …} envelopes are updated to match.
  • Nothing is committed by the builder; changes are left in the working tree for review.

4. Decisions

4.1 JSON-RPC compliance (DashiBase)

  • make → StructUtils.make.
  • Version member is "jsonrpc": "2.0" on every reply. A request whose jsonrpc is absent or not "2.0" is -32600 Invalid Request.
  • id must be an integer (or absent, for a notification). Anything else is -32600 with id: null — never a crash.
  • Batches are supported on /rpc and /rpc-probe: an array of requests answers an array of replies, notifications omitted, invalid elements answered with their own error, all-notifications answered with no body (204). An empty array is a single -32600 (already the case).
  • metadata is renamed data, coherently: the JSONError field, StructuredException's field, every test, and every frontend reader.

4.2 What happens to valid

valid currently does two jobs. Only one survives.

JobWhere todayDecision
Did the request succeed? valid:true in read/write/run replies (handlers.jl 239, 267, 344, 376, 860); valid:false in every failure body (failure_report, the empty-group failure at 762) Removed. result vs error says it. Other keys stay where they are ({document}, {path}, {text, parsed}, {kind, errors, issues, …}).
Is the document sound? validate-card (642) and the probe (830), beside issues Kept, inside result. A route that checks a document answers result even when the document is bad, which preserves today's UI experience.

Rule of thumb: a route that checks answers result with a verdict; a route that does answers error when it can't. Failures the probe already raises as errors (empty group, a document that does not build) stay errors.

JSON-RPC codeMeaningHTTP
-32700parse error400

Why per-code on the stream: Content-Type cannot tell a file from an error, because a stream may legitimately be JSON (fetch-data is). The client checks response.ok first. The mapping is one small table in middleware.jl, used only by JSONStreamHandler.

My call: /rpc-stream rejects a batch with a single -32600 (400), since a stream has exactly one body.

4.3b One GET route for large downloads

Decided: a GET route is kept so the browser can save a large file straight from the server, without the frontend holding it in memory. It covers get-processed-data only, the one large download that takes no params (the bundle needs a document, so it stays a POST through /rpc-stream + saveBlob, as today).

  • GET /get-processed-data, the same path main had, so the frontend link only needs API_ROUTES to keep it.
  • Implemented by building the JSON-RPC request on the server (method = "get-processed-data", empty params, integer id) and going through the same stream path. Status codes and headers are therefore exactly those of /rpc-stream (4.3). There is no second code path.
  • The response adds Content-Disposition: attachment; filename="processed-data.csv". Browsers ignore a link's download attribute across origins (UI on the dev server, API on another port). Without the header, the CSV opens in the tab instead of being saved.
  • The docstring says why it exists: a link cannot carry a JSON-RPC body, and only a download the browser makes itself (a link, with attachment) streams to disk. A fetch() always buffers the body in JavaScript.
  • A download the browser makes itself bypasses the page, so the UI could not show an error reply. It doesn't need to: the link renders only inside <Show when={result()}>, so it exists only after a successful run.

Considered and rejected: a hidden form POST to /rpc-stream. A form cannot send application/json, so the endpoint would have to accept a second, form-encoded body format.

4.4 Frontend

  • One request helper in requests.ts sends {jsonrpc:"2.0", id, method, params} to the right endpoint. It keeps postRequest's signature and returns the result unwrapped, {error: {code, message, data}} on failure, or the caller's default when the server could not be reached. My call: callers test isRpcError(reply) and read the failure through one helper, which returns error.data, or {errors: [error.message]} when there is no data. No handler result has a top-level error key, so the test is unambiguous.
  • Endpoint mapping: probe-pipeline → evaluate-pipeline on /rpc-probe; bundle-pipeline, fetch-data, get-processed-data → /rpc-stream; everything else → /rpc. Method names are otherwise unchanged.
  • postBlob/streamed reads check response.ok; on failure parse the JSON error envelope.
  • API_ROUTES (dev proxy list) becomes the three endpoints.
  • Readers of the old success flag switch to result/error: Documents.tsx 87, 106 (read/write), results.tsx 125 (run). Readers of the document verdict keep valid: probe.ts usableProbe, processing.tsx, stores.ts documentFindings. When the probe answers an error, the caller builds the probe store from error.data with valid: false, so those readers see what they see today.
  • An error with no data (bare handlers such as list-files, get-card-ir and fetch-data; protocol errors such as -32601 and -32700) shows error.message. Decided: this replaces today's misleading "Could not reach DashiBoard…", which these cases produced because they used to be bare 500s. "Could not reach" stays for null, meaning no answer at all.
  • The CSV link (results.tsx:351) keeps pointing at GET /get-processed-data (4.3b).
  • Frontend tests: mocks of server replies drop valid where 4.2 removes it, and failure mocks answer {error: {…}}. My call: tests already mock postRequest by route name, and the unwrapped result keeps every success mock valid as it is. Only failure mocks change.

4.5 ExperimentTracking moves onto DashiBase's layer

Decided: ExperimentTracking is updated in the same piece of work, so there is one JSON-RPC layer.

  • Delete src/api/json_rpc.jl. Use DashiBase's types and apply_handlers, probe_middleware and apply_middleware. The method apply_handlers(::AbstractDict, ::JSONFailure) from ET's copy is what DashiBase adopts to fix batches.
  • Its JSONHandler accepts a batch reply, as DashiBoard's does. Endpoints (api/v1, api/v1/probe) are unchanged, as is the always-200 rule (it does not stream). My call: ET keeps its own small JSONHandler rather than importing DashiBoard's, because ET depends on DashiBase, not DashiBoard.
  • Its probe drops valid = true and answers {source_vars, output_vars}. That valid is only ever true, since a failed probe throws, so it is a success flag (4.2).
  • Its tests send "jsonrpc":"2.0", read error.data, and stop reading result.valid.
  • Ordering. ET resolves DashiBase from DashiBoard's main, so the ET change lands after this branch merges. DashiBase stays at 2.0.0: this work completes the 2.0.0 release, which is not finished yet, so its breaking changes belong to that release. ET's compat is unchanged.
  • Out of scope: ET serving the UI. Its router registers only the two API routes. If it does serve the UI somewhere, that setup would also need the three /rpc* endpoints, as a separate change.

5. Test suite

5.1 What stays live (one server)

A single testset launches one server and checks: one /rpc call, one /rpc-probe call, one /rpc-stream call (success, and one failure for its status code), one GET /get-processed-data (status, Content-Type and Content-Disposition), the CORS response headers on one reply, and one OPTIONS preflight. Then closes. workspace.jl's launcher test keeps its process-level checks but posts a JSON-RPC body to /rpc (its "stopping stops the server" check must fail when the server is still up).

5.2 JSON-RPC layer (DashiBase, no server)

One parsimonious testset going through apply_handlers(handlers, ::String) with a toy handler table: a valid call; jsonrpc wrong; a string id; unknown method; parse error; and one batch mixing a call, a notification, an unknown method and an invalid element (asserting three replies in order). Roughly 30 lines.

  • /rpc-stream answers a batch with one -32600.
  • Read/write replies keep their keys minus valid (e.g. {document}), rather than returning bare values, to keep the frontend diff small.
  • postRequest returns the result unwrapped or {error}; callers test isRpcError; probe errors are mapped to a probe store with valid:false.
  • Frontend test mocks stay keyed by route name; only failure mocks change.
  • The GET download covers get-processed-data only, at its old path, through the stream path.
  • ExperimentTracking keeps its own JSONHandler; its probe drops valid.

8. Decided in discussion

  • Minimal source changes in DashiBase and DashiBoard are allowed where a goal requires them.
  • Fix make and the jsonrpc member; ids are integers only; batches are supported and tested; metadata→data everywhere.
  • validate-card and the probe keep valid plus issues inside result.
  • Status codes are per error on /rpc-stream (Content-Type can't tell a JSON stream from an error); /rpc and /rpc-probe always answer 200.
  • DashiBase stays at 2.0.0: these changes complete that unfinished release.
  • ExperimentTracking is updated in the same work; an error without data shows its message.
  • The bundle (pipeline + model/training configurations + extensions, zipped) stays a POST through /rpc-stream. It is small, so saveBlob is fine.
  • The CSV export uses a GET route with Content-Disposition: attachment, so the browser streams it to disk.
